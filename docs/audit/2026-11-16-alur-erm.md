(1) pasien datang, (2) ditanya keluhan, (3) dokter memeriksa dan mengerjakan, (4) dokter mengisi tindakan dan odontogram terisi otomatis, (5) dokter membetulkan odontogram bila perlu (opsional di pengaturan), (6) billing. Dokter tidak membuat rencana perawatan.

- **Tidak ada perbaikan** di audit ini. Satu tes regresi ditambahkan: `app/backend/tests/Feature/PatientJourneyTest.php`.

## Ringkasan

Tulang punggung alur berfungsi untuk kasus yang punya harga: tambal, cabut, scaling berjalan dari datang sampai lunas, dan odontogram mengikuti isian tindakan. Yang rusak ada di sambungan antar langkah dan di uang:

1. **Uang hilang diam-diam** di tiga tempat (tingkat harga, cabut tersimpan sebagai "Ada", kunjungan tanpa tagihan).
2. **Jalan buntu** untuk mahkota, PSA, implan: rekam medis sudah terkunci, kunjungan tidak bisa ditutup, dokter tidak bisa berbuat apa-apa.
3. **Keluhan tidak sampai ke dokter** di rekam medis, dan **status janji macet** setelah Selesai.

## Query rekonsiliasi

Semua harus menghasilkan nol. Dijalankan di database dev setelah seed bersih:

| # | Pemeriksaan | Hasil di data contoh |
|---|---|---|
| R1 | Kunjungan selesai dengan tindakan selesai berkode tanpa baris tagihan | **1** (data seed) |
| R2 | Tindakan selesai tanpa kode | 0 |
| R3 | Kunjungan selesai tetapi janji belum `done` | 0 di seed; **muncul di setiap kunjungan dari janji** (skenario A) |
| R4 | Catatan sudah ditandatangani tetapi kunjungan masih berlangsung | 0 di seed; **muncul di skenario D dan F** |
| R5 | Tagihan tanpa baris | 0 di seed; **muncul di skenario D dan F** |
| R6 | Kunjungan selesai tanpa tagihan sama sekali | **6** |
| R7 | Kode katalog terpetakan tanpa tarif | **9 kode** |

```sql
-- R1
SELECT COUNT(*) FROM procedure_record p JOIN visit v ON v.id = p.visit_id
WHERE v.status = 'selesai' AND p.status = 'selesai' AND p.state = 'final' AND p.procedure_code IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM invoice_line l WHERE l.procedure_id = p.id)
  AND NOT EXISTS (SELECT 1 FROM procedure_record s WHERE s.supersedes_id = p.id);
-- R3
SELECT COUNT(*) FROM visit v JOIN appointment a ON a.id = v.appointment_id WHERE v.status = 'selesai' AND a.status <> 'done';
-- R4
SELECT COUNT(DISTINCT v.id) FROM visit v JOIN clinical_note n ON n.visit_id = v.id JOIN clinical_note_version nv ON nv.note_id = n.id
WHERE v.status = 'berlangsung' AND nv.signed_at IS NOT NULL;
-- R6
SELECT COUNT(*) FROM visit v WHERE v.status = 'selesai' AND NOT EXISTS (SELECT 1 FROM invoice i WHERE i.visit_id = v.id);
-- R7
SELECT d.procedure_code FROM procedure_definition d WHERE JSON_LENGTH(d.conditions) > 0
  AND NOT EXISTS (SELECT 1 FROM tariff f WHERE f.tenant_id = d.tenant_id AND f.procedure_code = d.procedure_code);
```

## Wajib menurut regulasi vs kebiasaan software

Sumber: `docs/compliance.md` di repo. Saya tidak membaca peraturannya langsung; ini bukan nasihat hukum.

- **Rencana perawatan** sebagai langkah terpisah tidak disebut sebagai kewajiban di `docs/compliance.md`. Use case "Gigi" SATUSEHAT (v1.5) memang memuat "tindak lanjut", tetapi itu isi data, bukan langkah layar. Menyembunyikan tab-nya: **perlu dicek** oleh yang berwenang.
- **Keluhan** masuk "anamnesis", yang ada di daftar use case Gigi SATUSEHAT (pendaftaran, anamnesis, pemeriksaan fisik, pemeriksaan odontogram, diagnosis, tindakan, …). Jadi P1-1 bukan hanya soal kenyamanan: keluhan harus tersimpan di rekam medis, bukan hanya di janji.
- **Odontogram:** menurut `docs/compliance.md`, Permenkes 24/2022 tidak menyebut odontogram; acuannya use case Gigi SATUSEHAT dan Panduan Rekam Medis Kedokteran Gigi 2015, yang di dokumen itu sendiri masih bertanda "perlu dicek". Membuat langkah 5 opsional adalah keputusan klinik; apakah boleh dimatikan untuk pasien baru: **perlu dicek**.

## Keputusan S1: tindakan tanpa harga (Yohanes, 16 Nov 2026)

- Isian klinis tidak pernah ditolak karena harga. Dokter tetap bisa Selesai; rekam medis ditandatangani.
- Kunjungan dengan tindakan selesai tanpa harga **menunggu**: tidak bisa ditutup atau dibayar sampai pemilik mengisi harga di Pengaturan Klinik > Harga ("Tindakan tanpa harga"). Setelah harga diisi, menutup kunjungan menagih tindakan itu.
- Gratis = harga Rp0 yang diisi pemilik, bukan tindakan tanpa baris tagihan.
- Tindakan multi-kunjungan (PSA, mahkota): pasien **bayar per kunjungan**. Tiap kunjungan punya baris berharga sendiri (tahap/tingkat harga, dikerjakan di S2).
- Belum diubah: baris Rp0 masih minta persetujuan pemilik per baris (DEVIATIONS #56). Perlu keputusan apakah Rp0 dari daftar harga dianggap sudah disetujui.

Aplikasi lokal lain (Iconix, Medisy, DHealthcare) menulis alur: dokter pilih gigi + tindakan → odontogram mengikuti → kasir; tanpa rencana perawatan.

Arti untuk Bittodent ("bayar per kunjungan"):
1. Tidak ada pembanding yang punya harga per tahap bawaan. Pola mereka: **kode per tahap yang dibuat klinik** (Open Dental) atau **uang muka yang dipakai saat selesai** (CareStack, Open Dental).
2. Usulan S2: pemilik membuat tindakan tahap di daftar harga (mis. "PSA kunjungan 1", "PSA kunjungan lanjutan", "Mahkota: preparasi", "Mahkota: pemasangan"), masing-masing berharga (boleh Rp0). Dokter memilih tahap yang dikerjakan hari itu; kasir menagih per kunjungan. Tanpa tabel atau status baru.
3. Rp0 yang diisi pemilik di daftar harga sebaiknya dianggap sudah disetujui (sama dengan kode "no fee" Open Dental). Keputusan Yohanes diperlukan karena mengubah aturan #56.
4. Uang muka (bayar dulu, tindakan nanti) belum masuk MVP; dicatat sebagai pilihan nanti.
5. Dari CareStack: checkout sebaiknya menawarkan "jadwalkan kunjungan berikut" sebelum bayar (masuk S6).
